## v2.4 — 2026-08-06

**`deploy.sh` — розгортання/оновлення бота однією командою (з Proxmox-хоста):**
- Показує `diff -u` по кожному файлу перед записом; що не змінилось — не чіпає.
- **Конфіги з реальними даними не перезаписуються ніколи** (`targets.json`,
  `access.json`, `groups.json`) — лише повідомляє, чи файл ще збігається з шаблоном
  репозиторію, і пропонує встановити шаблон тільки якщо файлу в контейнері немає.
  `tgbot.env` не чіпається взагалі. Це головна гарантія скрипта: раніше при кожному
  ручному оновленні треба було пам'ятати, які файли пропускати.
- Бекап попередніх версій у `$APP_DIR/.backups/<дата-час>/` перед записом.
- Перевірки: наявність `pct`, стан контейнера, `venv`, `tgbot.env`; після запису —
  `py_compile` у venv контейнера і валідність JSON усіх конфігів (не пройшло →
  рестарту не буде).
- Окреме підтвердження на рестарт; після нього — перевірка живучості за стабільністю
  `MainPID` (кривий конфіг дає `exit 2` + `Restart=always`, тобто виглядає «активним»
  перші секунди — ловиться саме цикл перезапусків), і автовідкат із бекапу, якщо не
  піднявся.
- Прапорці: `--dry-run`, `--yes`, `--no-restart`, `--branch`; налаштування через
  змінні оточення або `deploy.local.conf` (у `.gitignore`).

## v2.3 — 2026-08-06

**Меню (кнопки замість команд):**
- Після `/start` користувач отримує постійну reply-клавіатуру — по кнопці на кожну
  доступну **саме йому** дію. Оператору з єдиним правом (`"block:ccm-sales"`) видно
  рівно одну кнопку: натиснув → підтвердив → готово, без команд і назв цілей вручну.
- Новий запис `btn` у реєстрі `ACTIONS` — підпис кнопки; `BTN_TO_KEY` розпізнає
  натискання (кнопки reply-клавіатури надходять звичайним текстом).
- Логіку входу в дію винесено в спільний `_start_action()`, який використовують і
  команди, і кнопки — поведінка (вибір цілі, підтвердження з TTL, перевірка прав,
  аудит) однакова для обох шляхів, без дублювання.
- У групових чатах бот мовчить на нерозпізнаний текст (щоб не реагувати на звичайне
  листування); у приватному — коротка підказка.

## v2.2 — 2026-08-06

**Групи (новий опційний `groups.json`):**
- `roles` — перевикористовувані набори дій для `access.json` (`"role": "duty"` замість
  дублювання `"actions"` для кожного оператора з однаковими правами).
- `target_groups` — іменовані групи цілей; скоуп дії може посилатись на групу
  (`"block:sales-dept"`) замість переліку конкретних цілей окремо, і додавання нової
  цілі в групу автоматично поширює вже видані права.
- `notify_groups` + нове опційне поле `"notify"` у `targets.json` — після успішного
  `/block` бот сповіщає вказану групу Telegram id (крім самого виконавця) окремим
  повідомленням; збій розсилки одному отримувачу не зупиняє решту.
- Усе розгортається в звичайні `дія:ціль` при завантаженні конфігу — `allowed()`,
  `visible_targets()`, `validate_actions()` не змінились. Файл повністю опційний:
  відсутній `groups.json` = поведінка достеменно як до цієї версії.

**bot.py:**
- Невідомий користувач (`⛔ Доступ заборонено`) тепер бачить власний Telegram id у
  відповіді — раніше єдиним способом дізнатись його був сторонній бот на кшталт
  @userinfobot.
- Виправлено витік `BOT_TOKEN` у `journalctl`: `httpx`/`httpcore` (HTTP-клієнт
  усередині `python-telegram-bot`) на рівні `INFO` логували повний URL кожного
  запиту до Bot API, включно з токеном у шляху — притишено до `WARNING`.

**RUNBOOK_universal_bot.md:**
- Задокументовано `groups.json` (розділ «Групи») + кроки деплою (3.2/3.3) і розширення.
- 1.3: виправлено шаблон політик користувача `tgbot` під RouterOS 7.x (політики `dude`
  там більше немає) + порада звіряти з `/user group print detail where name=full` перед
  копіюванням команди на будь-якій версії.
- 3.4: `SuccessExitStatus=1` — `python-telegram-bot` v21 (`run_polling`) інколи виходить
  з кодом 1 при штатній зупинці (відомий асинхронний нюанс), без цього рядка це зайво
  «з'їдало» слот `StartLimitBurst` на кожному рестарті.
- 0.3/0.4: конкретні команди замість опису (перевірка мережевої зв'язності, DHCP-пул,
  резервація адреси контейнера — опційний split пулу лише коли адреса дійсно в його межах).
- 2.2: альтернатива `hwaddr=<MAC>,ip=dhcp` для `pct create`, коли адресу контейнера
  резервують через статичний DHCP-lease (крок 0.4), а не задають статично в контейнері.

## v2 — універсальний бот (`RUNBOOK_universal_bot.md`)

Замінює v1: один сервер/один whitelist → реєстр цілей і гнучкі права.

| Було (v1) | Стало (v2) |
|---|---|
| Одна ціль, зашита в код/env | Реєстр цілей у `targets.json` — додавання серверa без зміни коду |
| Один whitelist на всі команди | Гнучкі права в `access.json`: user → перелік дій, зі скоупом на ціль (`block:srv-crm`) |
| Команди зашиті в код | Реєстр дій `ACTIONS` у `bot.py`: нова дія = один запис + функція |
| `/block` лише перемикає правило | `/block` = правило **+ авто-розрив сесій** → діє миттєво навіть із FastTrack |
| — | Нова дія `/kick` — миттєвий розрив активних сесій БЕЗ блокування нових |
| `/block_all`, `/unblock_all` | `/wg_off`, `/wg_on` (те саме, чесніша назва) |
| FastTrack-виключення по одній `dst-address` (1.4a) | `address-list` на всі цілі (v2.1: формалізовано як крок 1.5) |

Файли зросли з 2 (`bot.py`, `config.py`) до 4 (+ `targets.json`, `access.json`).
